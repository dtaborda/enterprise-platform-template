# Release Automation

## Purpose

This guide explains how GitHub Releases are produced in the Enterprise Platform repository, which token/scopes are required, and how to recover when `release-please` version files drift away from the actual published tags.

## Scope

- **Included**: normal release flow, token requirements, consistency guard, deadlock detection, automated reconciliation, manual recovery runbook
- **Excluded**: package registry publishing, monorepo independent versioning, application deployment

---

## Normal Release Flow

This repository uses `googleapis/release-please-action` in **manifest mode**.

### Phase 1 — release PR

On pushes to `main`, release-please reads conventional commits since the last release and opens or updates a release PR:

- title: `chore: release vX.Y.Z`
- label: `autorelease: pending`
- files updated:
  - `package.json`
  - `.release-please-manifest.json`
  - `CHANGELOG.md`

### Phase 2 — tag and GitHub Release

When that release PR is merged, the next Release workflow run creates:

- the git tag `vX.Y.Z`
- the GitHub Release `vX.Y.Z`

The PR label then moves from `autorelease: pending` to `autorelease: tagged`.

## Required Token Configuration

Preferred token: `RELEASE_PLEASE_TOKEN`

- Type: fine-grained PAT (or GitHub App token in a future hardening step)
- Required permissions:
  - `contents: write`
  - `pull-requests: write`

### Important gotcha

The workflow uses:

```yaml
token: ${{ secrets.RELEASE_PLEASE_TOKEN || secrets.GITHUB_TOKEN }}
```

This only falls back when `RELEASE_PLEASE_TOKEN` is **empty or unset**.

If the PAT exists but is expired, revoked, or under-scoped, GitHub Actions still passes a non-empty string to the action, so there is **no automatic fallback**. That is how the repository can end up with:

- release PR created successfully
- tag/release never created
- workflow still green unless extra guards exist

## Consistency Guard

The repository includes `pnpm release:check-consistency`, backed by `scripts/release/check-consistency.mjs`.

It verifies:

1. `.release-please-manifest.json` version
2. latest `v*` git tag
3. whether a legitimate `autorelease: pending` release PR exists inside a short grace window

### Expected states

- **Good**: manifest version equals latest tag
- **Temporarily acceptable**: manifest is ahead of latest tag **and** a release PR is still in a fresh pending window
- **Broken**: manifest is ahead of latest tag and there is no valid fresh pending release PR

## Release-please Deadlock

This section documents a self-perpetuating failure mode that has occurred twice (v1.3.0 and v1.4.0) and can leave `main` red for months if undetected.

### What it looks like

The CI logs contain one or more of these greppable error strings:

```
There are untagged, merged release PRs outstanding - aborting
```

```
Expected 1 releases, only found 0
```

```
[release-consistency] ERROR: manifest X is ahead of latest tag Y
```

### Root cause: release PR title pattern mismatch

The deadlock was **not** caused by expired tokens or transient API errors. It was a configuration bug in `release-please-config.json`, which is why it recurred on every release rather than occasionally.

Two different options control the two halves of the round trip:

| Option | Controls |
|--------|----------|
| `group-pull-request-title-pattern` | The title release-please **writes** when `separate-pull-requests` is `false` (a grouped manifest PR) |
| `pull-request-title-pattern` | The pattern release-please **reads** to recover the version from a merged release PR |

`group-pull-request-title-pattern` was never set, so release-please fell back to its default (`chore: release ${branch}`) and produced PRs titled `chore: release main`. Meanwhile it tried to parse them back with `chore: release v${version}`. The title carries no version, so the parse failed and release-please refused to tag.

The upstream docs are explicit that these patterns "must allow the system to parse the component name and version from the title or body".

The historical record matches exactly:

| Release PR | Title | Parseable | Outcome |
|------------|-------|-----------|---------|
| #5 | `chore: release v1.1.0` | Yes | Published automatically |
| #10, #13, #64, #70, #144, #155 | `chore: release main` | No | Required manual recovery |

### The self-perpetuating cycle

1. The release PR merges, bumping `.release-please-manifest.json` to version X.
2. release-please cannot parse the version from that PR's title, so tag `vX` and the GitHub Release are never created.
3. The PR keeps the label `autorelease: pending`.
4. From this point on, **every** push to `main` fails: release-please aborts with `There are untagged, merged release PRs outstanding - aborting`, and the consistency guard (`check-consistency.mjs`) exits 1.
5. The failure is self-perpetuating. No conventional commit, re-push, or workflow retry can break the cycle. `main` stays red until a human (or the reconcile tool) creates the missing release.

> **Warning**: The consistency guard's 2-hour grace window (`RELEASE_PENDING_GRACE_HOURS`) **masks a freshly formed deadlock**. The run immediately after the release merge reports success and the guard reports OK; `main` only turns red once the window expires. Do not read a green run immediately after merging a release PR as proof that the release published — verify the tag exists.

> **Warning**: This deadlock is otherwise invisible unless the failure alerting job is active. Without it, `main` can stay broken indefinitely — the v1.4.0 incident went unnoticed from 2026-06-08 to 2026-08-30.

### Safety gate

The reconcile tool (`scripts/release/reconcile.mjs`) refuses to act unless **exactly one** merged release PR's manifest-at-merge-commit matches the current manifest version. It reads `.release-please-manifest.json` at the PR's merge commit SHA via `git show` and compares it to the current value. This prevents publishing a bogus release from an unrelated PR that happens to share the `autorelease: pending` label.

## One-click Repair (Automated Reconciliation)

The Release workflow supports a `workflow_dispatch` trigger with an `apply` input that runs the reconcile script.

### Step 1 — preview (dry-run)

1. Go to **Actions > Release > Run workflow**.
2. Leave `apply` as `false` (the default).
3. Run the workflow.
4. Check the step summary — it shows what the tool WOULD do without mutating anything.

### Step 2 — apply

1. Verify the dry-run output is correct (correct PR, correct merge commit, correct version).
2. Rerun with `apply` = `true`.
3. The tool creates the missing GitHub Release, tags the correct commit, and updates the PR labels.

### What happens after reconciliation

- The consistency guard (`check-consistency.mjs`) passes again.
- release-please resumes normal operation on the next push to `main`.
- If a tracking issue with the label `release-pipeline-broken` is open, close it manually after confirming the fix.

## Manual Recovery Fallback

If the automated reconciliation cannot resolve the issue (ambiguous PRs, corrupted manifest, etc.), use these manual commands:

### Prerequisites

Identify:
- the manifest version (`M`) from `.release-please-manifest.json`
- the merge commit SHA of the release PR that produced that version
- the PR number

### Commands

```bash
# 1. Extract release notes from CHANGELOG.md at the merge commit
git show <merge-commit-sha>:CHANGELOG.md > /tmp/changelog.md
# Manually extract the section for version M

# 2. Create the missing GitHub Release
gh release create vM --target <merge-commit-sha> --title vM --notes-file /tmp/release-notes.md --latest

# 3. Fix the PR labels
gh pr edit <N> --remove-label "autorelease: pending" --add-label "autorelease: tagged"

# 4. Verify
pnpm release:check-consistency
```

Always verify the target SHA against `CHANGELOG.md` before creating the missing tag.

## Failure Alerting

The Release workflow includes an `alert-on-failure` job that runs when the `release-please` job fails on a push to `main`.

- It opens (or updates) a GitHub issue with the label `release-pipeline-broken`.
- The issue includes the failing run URL, commit SHA, and a pointer to this runbook.
- It is idempotent: repeated failures add comments to the existing issue instead of opening new ones.
- The label is created automatically if it does not exist.

## Recovery Runbook

Use this when version files were bumped but the actual tag/release was never published.

### Symptoms

- `package.json` and `.release-please-manifest.json` show a version newer than the latest git tag
- `CHANGELOG.md` already contains the new version entry
- a merged PR still has `autorelease: pending`
- the Release workflow shows green but no GitHub Release exists

### Recovery strategy used for the `1.3.0` incident

For this repository, the chosen default recovery strategy is:

1. verify the intended merge commit for the missing version
2. create the missing remote tag on that commit
3. create the GitHub Release for that tag
4. remove `autorelease: pending` and add `autorelease: tagged`
5. rerun consistency verification

### Example commands

```bash
gh release create v1.3.0 --target efd81fe --title v1.3.0
gh pr edit 70 --remove-label "autorelease: pending" --add-label "autorelease: tagged"
pnpm release:check-consistency
```

Always verify the target SHA against `CHANGELOG.md` before creating the missing tag.

## Rotation Checklist

- Record the token owner and expiration date in the maintainer notes.
- Rotate the token before expiration.
- After rotation, run a low-risk release workflow verification.
- Never assume a configured PAT will fall back automatically to `GITHUB_TOKEN`.
